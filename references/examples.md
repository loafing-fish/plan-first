# 方案示例

四个场景，展示方案该细到什么程度、什么时候停下来。示例中的路径和命令是示意，实际执行前要换成项目里的真实值。

## 示例 1：需求含糊（「给博客加个搜索」）

**用户说**：给博客加个搜索吧。

**不要直接做**。先确认真正影响方案的问题，再给分叉方案：

```text
## 任务理解

目标：让读者在博客里按关键词找到文章。
交付物：站内搜索框 + 结果列表；移动端可用。
范围内：按标题、摘要、标签搜索现有文章。
范围外：全文检索服务、搜索排行榜、后台管理。

## 关键假设

1. 博客是静态站，文章在 content/posts/*.md；没有后端。
2. 文章数量在几百篇以内，可以在浏览器里建索引。
3. 搜索只需要中文和英文，不需要分词服务。

## 需要你决定

1. 搜索范围：只搜标题和标签，还是连正文一起搜？
   - A. 标题 + 标签（快、结果准）
   - B. 标题 + 标签 + 正文（更全，索引更大）
   - 建议 A；正文搜索等文章过千篇再考虑。
2. 结果为空时：显示「没有找到」还是推荐最近文章？
   - 建议显示「没有找到」+ 最近三篇。

## 执行步骤（按 A 走）

1. 读 content/posts 的 frontmatter，确认可索引字段 → 字段清单 → 用三篇文章抽查。
2. 加一个构建时生成的搜索索引 → public/search-index.json → 检查文件大小和条目数。
3. 加搜索框和结果列表 → 页面组件 → 本地起站点，搜三个关键词验证。
4. 处理空结果、转义特殊字符、键盘操作 → 组件 → 手动点一遍。
5. 跑构建和现有测试 → 命令输出 → 构建通过、无新增警告。

## 风险与回滚

- 风险：索引文件过大，首屏变慢。降低：只索引标题、摘要、标签；超过 200 KB 就改成分片加载。
- 回滚：删除新增组件和索引生成脚本，恢复原页面；不涉及数据迁移。

## 验收

- `pnpm build` 通过。
- 搜索「部署」「Next.js」「不存在的词」各一次，结果符合预期。
- 移动端宽度 375px 下不遮挡导航。

确认：回复「A」或「B」，以及空结果的处理方式；确认后我开始。
```

要点：需求含糊时，方案的重点是**把分叉摆出来**，不是假装已经知道答案。

## 示例 2：修 bug（「登录偶尔失败」）

**用户说**：登录偶尔失败，刷新一下又能进，帮我修一下。

```text
## 任务理解

目标：找到登录偶发失败的原因并修掉，不靠重试掩盖。
交付物：根因说明 + 修复提交 + 回归测试。
范围内：登录接口、token 刷新、前端跳转。
范围外：重写认证系统、改第三方登录。

## 关键假设

1. 「偶尔」集中在 token 快过期时；如果是网络问题，方案要改。
2. 生产日志可读，能拿到失败请求的时间点和状态码。
3. 本地能复现，或至少能用测试模拟并发刷新。

## 现状与未知

已知：
- 登录入口在 src/auth/login.ts。
- 失败时前端收到 401，但没有保留响应体。

待查：
- 失败请求的 token 剩余有效期 → 查日志。
- 是否同时发了两个刷新请求 → 查 Network / 加临时日志。
- 服务端是否把旧 refresh token 立即作废 → 读 auth 服务代码。

## 执行步骤

1. 复现：用两个并发请求打刷新接口 → 记录状态码和响应体 → 至少复现一次，或证明本地无法复现。
2. 定位：对照日志时间线，确认是「并发刷新」还是「过期判断」→ 根因假设 → 用一次实验证伪或证实。
3. 修复：只改认证模块；并发刷新只允许一个请求，其余等待结果 → diff → 代码审查。
4. 回归测试：加一个并发刷新测试，修复前必须失败，修复后通过 → 测试输出。
5. 验证：本地登录、刷新、退出各走一遍 → 截图或日志。

## 风险与回滚

- 风险：改刷新逻辑导致所有人被登出。降低：保留旧 token 的宽限期；先在本地和预发验证。
- 回滚：回退认证模块提交；不改数据库结构。

## 验收

- 新增测试在修复前失败、修复后通过。
- 并发刷新只发一次网络请求。
- 正常登录和退出不受影响。

确认：回复「继续」开始；如果你知道失败发生的时间段，直接告诉我，能省一步。
```

要点：修 bug 的方案先写**怎么证明根因**，再写怎么改。不要一上来就「修改登录逻辑」。

## 示例 3：高风险操作（「清理旧日志」）

**用户说**：把 2024 年以前的日志都删了，服务器快满了。

```text
## 要动什么

- 对象：生产服务器 prod-01 的 /var/log/app/ 下 2024-01-01 之前的 *.log
- 操作：删除文件
- 影响：这些日志将无法恢复；正在写入的当前日志不受影响。
- 不可逆点：删除后只能从备份恢复。

## 为什么

磁盘占用 92%，其中旧日志约 38 GB。先清旧日志，再排查为什么没有轮转。

## 怎么做

1. 盘点：列出匹配文件、总大小、最早和最晚时间 → 输出清单 → 确认没有正在写入的文件。
2. 备份：把清单打包到 /backup/logs-2024.tar.zst → 解压一个文件验证 → 确认备份可读。
3. 预演：用 `find ... -print` 只打印不删除 → 数量与第 1 步一致。
4. 正式执行：按清单逐个删除，不用通配符一把梭 → 记录删除数量。
5. 验证：磁盘占用、应用日志写入、错误率 → 前后对比。

## 回滚

- 命令：从 /backup/logs-2024.tar.zst 解压回原路径。
- 回滚后验证：文件数量、权限、应用能正常写日志。

## 确认

请明确回复「确认清理 /var/log/app 下 2024 年前的日志」。只说「继续」不算确认。
```

要点：红色操作要写清**精确对象、影响、备份、预演、回滚**。确认不能靠一句「继续」带过。

## 示例 4：用户说「直接做」（小改动）

**用户说**：按钮文案改成「立即购买」，直接做，不用方案。

```text
理解：把商品页主按钮文案从「购买」改成「立即购买」，只改文案，不动样式和逻辑。
步骤：改组件文案 → 跑相关测试 → 截图确认。
风险：低；回滚是改回原文案。
开始执行。
```

这属于黄色操作（会改文件），但用户明确授权连续执行，所以一句话方案后直接做。

但如果改的时候发现按钮文案来自国际化文件、还要同步另外三种语言，这就超出了「只改文案」的范围：

```text
停一下：文案在 i18n 文件里，涉及 zh/en/ja/ko 四份，不是单文件改动。
新方案：改四份文案 → 跑 i18n 校验 → 截图。
这会多改三个文件；确认后我继续。
```

要点：授权连续执行，不等于授权扩大范围。

## 反例

| 反例 | 问题 |
|---|---|
| 「我会先分析代码，然后修复问题，最后测试。」 | 没有对象、产物、验证，无法判断是否理解正确。 |
| 「理解：用户想加搜索。步骤：1. 写代码 2. 测试。」 | 把请求抄了一遍；没有假设、范围、风险。 |
| 「方案：1. 删除旧数据 2. 清理缓存。」 | 没写删什么、影响谁、怎么备份、怎么回滚。 |
| 「我先执行看看，有问题再调整。」 | 方案出现在动作之后，已经失去确认的意义。 |
| 「有十个问题要确认……」 | 把能自己查的事实推给用户；只问真正阻塞、且会改变方案的问题。 |
| 「预计需要 2 小时 15 分钟。」 | 虚假精确；写依赖和范围，或给区间。 |
