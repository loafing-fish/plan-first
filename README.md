# plan-first

一个让 AI 在动手前先讲清楚的 Agent Skill：任务理解、关键假设、执行步骤、风险与验收标准，确认后再执行。

## 它解决什么问题

AI 最常见的失败不是不会做，而是：

- 理解错了，却已经改完文件；
- 方案只存在模型脑子里，用户没机会在动手前纠正；
- 顺手重构、顺手升级、顺手改无关文件；
- 删除、发布、改权限之前没有单独确认；
- 交付时只说「做好了」，没有对照最初的方案。

`plan-first` 把「方案」变成执行前的一次检查点：先让用户看到 AI 以为的任务是什么、准备怎么做、哪里可能出错，再决定是否放行。

## 它会要求 AI

1. 用自己的话复述目标、交付物、范围和成功标准；
2. 写出关键假设，以及还不知道、准备怎么查的部分；
3. 给出带产物和验证方式的执行步骤；
4. 标出风险、不可逆操作、备份和回滚；
5. 按风险分级停下来等确认，而不是一律直接开做；
6. 交付时对照方案，说明完成、变更和未验证的部分。

## 安装

仓库根目录就是 skill 目录，入口是 `SKILL.md`。

### DSH 及其他扫描 `.agents/skills` 的工具

用户级安装：

```powershell
git clone <本仓库地址> "$HOME\.agents\skills\plan-first"
```

项目级安装：

```powershell
git clone <本仓库地址> ".agents\skills\plan-first"
```

DSH 也会扫描 `~/.dsh/skills`，放在那里同样有效。安装后新开一个会话，让 skill 目录被重新扫描。

### Claude Code

```powershell
git clone <本仓库地址> "$HOME\.claude\skills\plan-first"
```

### 其他 Agent Skills 兼容工具

把整个目录放进该工具的 skills 根目录即可，不需要改文件名或目录结构。

## 使用

显式调用：

- 「用 plan-first 先给方案，别动手」
- 「先说说你打算怎么做」
- 「plan first」
- 「先给方案」

也会在以下场景自动触发：多步骤任务、会改文件或跑命令的任务、需求含糊、影响面大、不可逆操作。

## 目录结构

```text
plan-first/
├── SKILL.md                    # 唯一入口：触发条件、规则、确认门
├── README.md                   # 安装、设计说明、版本策略
├── CHANGELOG.md                # 版本变更记录
├── LICENSE
├── .gitignore
└── references/
    ├── plan-template.md        # 完整版 / 精简版 / 只读版 / 高风险版 / 执行后对照
    └── examples.md             # 四个场景示例 + 反例
```

`SKILL.md` 保持短而可执行；长模板和示例放在 `references/`，由 AI 按需加载，避免每次调用都把全部内容塞进上下文。

## 设计取舍

**默认停下来等确认。** 方案的价值在于「动手前能被纠正」。如果 AI 说完方案立刻开做，用户很难拦住。只读任务和用户明确授权连续执行的任务例外，减少不必要的往返。

**按风险分级，而不是一刀切。** 绿色（只读、无副作用）可以直接做；黄色（写文件、装依赖、提交）默认确认；红色（删除、发布、改权限、花钱）永远单独确认，即使用户说过「直接做」。

**先查再问。** 能通过读代码、看日志、跑命令确认的事实，不推给用户。只问真正阻塞、且会改变方案的问题，一次最多三个。

**方案是承诺，不是仪式。** 每一步要有产物和验证；交付时对照方案。没有验证方式的步骤，通常说明还没想清楚。

**不绑定具体工具。** 规则只描述行为，不依赖某个模型、IDE 或框架。任何能读取 `SKILL.md` 的 agent 都可以用。

**不写校验脚本。** 这是行为约束，不是格式检查。真正的硬约束应该由 CI、测试、代码审查或权限系统兜底；一个检查「有没有写方案」的脚本很容易被形式化绕过。

## 版本管理

- 语义化版本：`MAJOR.MINOR.PATCH`；
- 每次发布更新 `CHANGELOG.md`；
- 用 Git tag 标记发布版本，例如 `v1.0.0`；
- 当前版本：`v1.0.0`。

版本号规则：

- **MAJOR**：破坏兼容的行为变化，例如不再默认等待确认、修改触发条件；
- **MINOR**：新增规则、模板、风险级别或示例；
- **PATCH**：措辞修正、错别字、示例补充，不改变行为。

## 自定义

- 觉得确认太频繁：把「黄色」改成可连续执行，但保留红色操作的单独确认。
- 团队使用英文：翻译 `SKILL.md` 的规则和模板；目录结构不变。
- 项目有特殊约束：写进项目的 `AGENTS.md` 或等价规则文件，不要改 skill 本体，否则升级会冲突。
- 想加自己的方案格式：在 `references/plan-template.md` 里加一节，保持 `SKILL.md` 的精简。
